# UnitCall 设计优化评估

> 已被 [Unit 域统一重设计](unit-domain-redesign.md) 取代。以下保留为第二轮评审历史；结果所有权与子树交付的候选方案已在新主稿中作出选择。

状态：第二轮设计评审，未修改 ABI 或实现。本稿调整上一稿的建议：优先让 Join 返回它等待的退出结果，通用 Inspect 降为备选；不能据此宣称已经解决全部子树结果需求。

Team 的字段职责、方法对偶与命名对称要求见 [Team 字段与方法对偶评审](team-design-review.md)。这部分必须与调用契约共同确定，不能先在 Team 上补字段和方法来迁就 ABI。

## 结论

上一稿的 Inspect 暴露了 TaskState、stopped、暂停继承位、创建者、关系修订和退出记录。Shell 真正需要的是：确认停止/恢复、获得成员退出原因、发现辅助任务异常、可靠回收。这不要求通用任务快照。

更好的设计顺序是先定义生命周期对象及结果所有权，再决定调用入口。不能以“少了四个调用”作为唯一评价，也不能把通用状态枚举当作可靠的完成协议。

## 收敛为三条轴

| 轴 | 调用 | 契约 |
| --- | --- | --- |
| 创建 | Build、Spawn | Build 创建 Team；Spawn 创建 Held task，发布前预留所需元数据 |
| 执行 | Embark、Debark、Slay | 首次放行/恢复、暂停、终止；成功边界与权限显式定义 |
| 收尾 | Join、Oust | 等待退出并取得结果；放下已完成对象及其保留记录 |

SelfId/Sire/HeirCount/Heir 是血缘事实，Fall 是能力到达通知。它们不因 Shell 需求扩大职责。

## 1. 共用目标，不共用未经定义的权限

保留上一稿的 ControlTarget：

```rust
enum ControlTarget {
    Task(TaskId),
    Tree(TeamId),
}
```

Embark/Debark 使用该目标。任务停止与子树暂停是两个独立门：恢复其中一个不能清掉另一个；恢复子树不能放行 Held task。Debark(Tree) 成功必须确认所有运行成员离槽，新建/唤醒成员也受门约束。

Slay 保持单 task 参数。不能仅为了统一签名就加入 Tree，因为 Room::Doom 有独立能力门；相同目标类型不意味着相同授权。

不引入 `Control { action, flags }` 一类总括调用：它减少枚举项，却把不同的成功条件、权限和失败副作用隐藏到参数里。

## 2. Join 返回所等待的结果

上一稿把 Join 的 bool 当作不可改变的边界，因而另加 Inspect。这项限制没有必要。必须保留的是“收尾完成”的语义，而不是 bool 的返回形状。

建议主任务接口：

```rust
struct TaskExit {
    cause: ExitCause,
    reason: Reason,
}

enum JoinReply {
    Pending,
    Reaped(TaskExit),
}

Join { task: TaskId, millis: Wait } -> UnitResult<JoinReply>
```

- Pending 表示本次等待期限内没有取得收尾完成事实；Wait::POLL 立即返回，Forever 等待完成。
- Reaped 同时证明退出 hooks 已完成，并提供这个 task 的退出原因。仍不承诺物理内存已经回收。
- 非零 reason 是数据，不是 UnitFail；无权、无有效记录等才是接口错误。
- cause 来自真正的 Reap/强制终止/级联/fault 路径；不能通过用户提供的 reason 数值伪造。
- 不提供 Running/Blocked/Paused 等调度状态，不把 Join 改成通用状态查询。

返回可用三个寄存器：a0 为 Pending 或退出 cause 标签，a1 为 reason，a2 保留为 0。错误仍使用现有负码约定。旧包装若只关心收尾，可从 Reaped 推导 bool；原始 ABI 必须整体迁移，不能让旧镜像误解新返回值。

这一改变替代主任务“Join 后再 Inspect”的两次读取，减少不同入口之间的寿命竞态；没有新增操作号。

## 3. 结果所有权必须先解决

Join 返回 reason 本身很简单，困难在于 task 物理回收以后谁还持有结果。

应把“小型退出记录”和 Task/Space 寿命分开，在 Spawn 发布之前预留。退出只填槽，不临时分配；读取不能依赖诊断环，也不能用 Denied 推断正常退出。

上一稿“全部后代结果保留到根 Team Oust”存在实际问题：长期存活的 Team 不断创建和回收线程时，即使内存已经释放，记录仍持续增长，最终会耗尽额度。因此 Oust 整个 Team 不能是唯一释放方法。

结果释放必须在以下两个方案中明确选择，不能由实现自行决定：

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| Join 非消费；显式放下 task 退出记录 | 允许重复读取、多个等待者；符合当前 Join 的观察性质 | 要设计清楚记录的释放入口及授权，可评估把 Oust 扩展为结果记录/Team 两种目标 |
| Join 由唯一结果 owner 消费 | 创建→退出→领取自然闭合；领取后立即释放结果槽 | 改变 Join 的权限、重复调用及多等待者语义；还需要 owner 放弃领取的回收路径 |

倾向第一种，因为现有调用方广泛把 Join 当作非消费观察。不过，扩展 Oust 也属于正式 ABI 设计，不能把 `TaskId` 塞进现有 `TeamId` 参数或暗用标志位。

这一选择直接决定长期任务创建是否可持续，优先级高于新增一个方便查询的 Inspect。记录额度、owner 死亡、放下时的并发等待、迟到结果、重复放下，都必须有同一生命周期答案。

## 4. 子树辅助任务结果是独立的缺口

主任务 Join 已足够返回每个命令成员的退出结果，但单任务 Join 不能发现“主任务仍运行，后代辅助任务先故障”。不能把这个缺口藏起来。

不建议按上一稿把所有后代 TaskState 与暂停位分页导出，再由 System 持续扫描。应比较两种真正针对完成事实的模型：

- **子树完成通知**：对合法控制根订阅内核发布的 task 退出事实；明确来源、可靠记录、消费/放弃和队列预算。通知与结果所有权可以共用生命周期机制。
- **只读完成记录查询**：如果当前资源模型无法承载可靠通知，只提供 task 退出记录，不提供调度状态、关系版本或暂停位；查询同样必须有明确释放路径和预算。

这两种都不能简单使用“子程序自愿向父方发消息”：异常、强制终止和发送失败时仍需要可靠的内核退出事实。

也不建议让 `Join(Tree)` 在任意辅助任务退出时就返回“整个子树完成”。若选择等待子树事件，必须明示它是“下一个成员完成事件”，而不是沿用原有收尾完成含义。

所以，本稿推荐 **先定结果记录的所有权，再设计子树完成事实的交付**。确定之前不默认增加 Inspect，也不承诺零新增调用即可保持所有现有作业控制保证。

## 5. Observe 不属于 Unit

保留上一稿的删除建议。结果读取、订阅或消费不改变退出原因，也不改变内核诊断。

Control 决定主任务及辅助任务结果怎样影响实例；Job 决定一个成员失败是否取消其他成员；测具决定预期退出怎样影响整机验收。不能将这些决策编码成 Team 的 observed 位。

需要特别验证命令退出 17 与服务故障同时发生时，前者可以是预期结果，后者仍使场景失败。移除 Observe 必须同步设计判定路径，不能只删除失败账。

## 6. 其他 UnitCall 的优化边界

HeirCount 与按 index 的 Heir 两次枚举在关系变化时没有固定快照。未来可评估按稳定 TeamId 游标批量列举直接 heir，替代这两个调用；这不是本轮 Shell 作业控制的前置条件，不和暂停改造捆绑。

SelfId 与 Sire 虽都是无参读取，但语义清楚，没有必要为了调用数量将它们包装成多属性查询。Fall 只保留能力到达通知，不扩展为“任何 Unit 状态变化”。Build 与 Spawn 必须分开，因为中间还要映射镜像、授予能力，然后才首次放行。

## 优化后的评审顺序

1. Task 与子树的停止门、授权和首次放行边界。
2. Join 返回 TaskExit；记录 owner、重复读取与释放方式。
3. 子树辅助任务完成事实的交付方式、预算和 owner 死亡清理。
4. 删除 Observe 后的场景判定。
5. 固定完整操作号、寄存器布局、失败行为与所有调用方迁移。

当前可以确定的是优化方向；第 2、3 项仍是待评审决策。因此本稿是设计评估，不是已证明可以替换 PR 的实现方案。
